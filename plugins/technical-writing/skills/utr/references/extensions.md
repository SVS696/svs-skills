# Расширения для технических документов

Выберите раздел по назначению текста. Правила ниже задают прикладной профиль редактора. Когда проект принял конкретный стандарт или форму документа, сохраните их требования и поля. Номера применимых источников и редакции указаны в [указателе](sources.md).

## Системное требование и критерий приёмки

1. Найдите источник и идентификатор требования, если они есть. Различайте потребность заказчика, требуемое поведение, предлагаемое решение и результат испытания.
2. Составьте фразу по смыслу. Для события подходит форма «Когда происходит событие, компонент должен выполнить действие». Для состояния — «Пока действует условие, компонент должен обеспечивать результат». Для разрешения — «При условии роль вправе выполнить действие». Для безусловного требования сразу назовите исполнителя и действие. Не добавляйте событие только для заполнения формы.
3. Если источник требует два изменения в одной транзакции, сохраните одну гарантию результата и опишите обе записи. Если результат един для нескольких условий, уточните, достаточно ли одного или нужны все.
4. Опишите проверку через начальные данные, действие и наблюдаемый результат. Сохраните метод и допуски из источника. Если для граничного случая результат не задан, вынесите вопрос.
5. Для принятого проектом ГОСТ Р 59194-2020 учитывайте область применения. Пункты 5.2 и 5.3 связывают требования с проверкой, критериями, подтверждающими документами и согласованием. Пункт 6.1.2 предусматривает организационные правила для текста требований. Пункт 6.2.2 требует устойчивого уникального идентификатора. При редактуре сохраните его, связи и версию. Содержание исходных требований и прохождение проверки подтверждаются разными источниками.

**Пример.** «Когда оператор повторно передаёт запрос с тем же `request_id`, сервис должен вернуть исходный `operation_id`». Для проверки сравните два ответа. Если исходное требование касается только идентификатора, вопрос о повторной записи данных остаётся отдельным.

Паттерны EARS помогают выбрать конструкцию по событию, состоянию, функции или нежелательной ситуации. Этот метод и ISO/IEC/IEEE 29148 относятся к инженерии требований. Для обычной редактуры достаточно исходного требования и принятого в проекте языка. [EARS](https://alistairmavin.com/ears/) · [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)

## Техническое задание на автоматизированную систему

Если заказан ГОСТ 34.602-2020, разделите работу над языком и проверку структуры. Проверьте наличие обязательных разделов по п. 4.1. Они охватывают общие сведения, цели и назначение, объект автоматизации, требования к системе, состав работ, порядок разработки, контроль и приёмку, подготовку объекта к вводу, документирование и источники. В итоговом ТЗ сохраните заголовки и порядок применимой формы.

- При отсутствии требований по разделу сохраните раздел с записью об их отсутствии. Если сведения пока неизвестны, зафиксируйте, что нужно уточнить. Эти ситуации дают разные результаты.
- По п. 4.2 проверьте применимость разрешённых изменений структуры. Оформление части материала в приложении должно сохранять связь с основным разделом. Для ТЗ на составную часть учитывайте исключение для сведений, которые повторяют ТЗ на систему.
- При редактуре показателя сверьте значение и допуски с п. 5.3 и источником. У проекта может быть диапазон, предельное отклонение или один предел. Не восстанавливайте недостающий предел догадкой.
- Если изменяется утверждённое ТЗ через дополнение, сохраните адрес изменяемого пункта, операцию изменения и новую редакцию по п. 5.8.

**Пример.** При заданном требовании «не более 3 с после подтверждения импорта» сохраните число, единицы и событие. В разделе контроля опишите, от какого подтверждения до какого наблюдаемого события измеряют срок. Если конечная точка неизвестна, задайте вопрос владельцу требования.

## API и сетевой протокол

Сохраните метод, путь, код ответа, тип поля, регистр, единицы и форму значения на проводе. Различайте обязательность поля, допустимость `null`, пустое значение, отсутствие поля и значение по умолчанию. Отдельно проверьте версию контракта, действия сторон, повтор, тайм-аут и порядок сообщений, если они определены в источнике.

Если документ явно принимает BCP 14, сохраните оригинальные нормативные слова и регистр. По RFC 2119 и RFC 8174 `MUST`, `REQUIRED` и `SHALL` задают обязательное условие, `MUST NOT` и `SHALL NOT` задают запрет. `SHOULD` и `RECOMMENDED` допускают обоснованное отступление после рассмотрения последствий. `SHOULD NOT` и `NOT RECOMMENDED` допускают обоснованное исключение из отрицательной рекомендации. `MAY` и `OPTIONAL` разрешают выбор. При таком соглашении специальное значение имеют формы в верхнем регистре. Строчные слова трактуйте по контексту. В русском пояснении передайте ту же силу. Не добавляйте BCP 14 в договор, который его не принимал. [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) · [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)

**Пример.** Если контракт разрешает (`MAY`) вернуть `Retry-After` вместе с `429`, запишите «Сервер вправе включить заголовок `Retry-After` в ответ `429`». Случай без заголовка по этому условию допустим.

## Руководство, скилл и описание решения

- **Действие пользователя.** Укажите исходное состояние, точную надпись в интерфейсе, действие и проверяемый признак завершения. Поставьте существенное исключение у того шага, который оно меняет. Метки опасности и предусмотренные остановки сохраняйте вместе с командой.
- **Скилл.** Укажите вход, разрешённое действие, место результата и условие завершения. Если скилл только проверяет, сохраните эту границу. Термин «проверено» требует наблюдаемого результата проверки.
- **Архитектурное решение.** Укажите исходное ограничение, выбранный механизм, причину и предел применимости. Если второй вариант отвергли из-за стоимости, не превращайте это решение в утверждение о его технической невозможности.
- **Протокол испытания или совещания.** Зафиксируйте, кто что наблюдал или решил, при каких условиях и на каком основании. Если есть исполнитель, срок или критерий приёмки, сохраните их. Слова о будущем действии не подтверждают его выполнение.
