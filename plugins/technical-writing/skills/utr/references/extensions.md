# Расширения для технических документов

Откройте раздел о документе, который вы готовите. Берите из примера только то, что подходит к вашей задаче. Когда проект принял конкретный стандарт или форму документа, сохраните их требования и поля. Номера применимых источников и редакции указаны в [указателе](sources.md).

## Постановка на изменение

Опишите, что изменится и как проверить результат. Опустите необязательные разделы, к которым у задачи нет требований. Если нужное для реализации условие ещё не определено, запишите конкретный вопрос. Например, если меняется только название кнопки, укажите старую и новую надписи. Раздел про интеграции для такой задачи не нужен.

Если заказчик или проект прямо требует ТЗ на автоматизированную систему по ГОСТ 34.602-2020, используйте [памятку по форме ТЗ](tz-34-602.md).

## Системное требование и критерий приёмки

1. Найдите источник и идентификатор требования, если они есть. Различайте потребность заказчика, требуемое поведение, предлагаемое решение и результат испытания.
2. Составьте фразу по смыслу. Для события подходит форма «Когда происходит событие, компонент должен выполнить действие». Для состояния — «Пока действует условие, компонент должен обеспечивать результат». Для разрешения — «При условии роль вправе выполнить действие». Для безусловного требования сразу назовите исполнителя и действие. Не добавляйте событие только для заполнения формы.
3. Если источник требует два изменения в одной транзакции, сохраните одну гарантию результата и опишите обе записи. Если результат един для нескольких условий, уточните, достаточно ли одного или нужны все.
4. Если нужен критерий приёмки, опишите наблюдаемый результат и необходимые условия его проверки. Перенесите заданные допуски и метод. Уточните неопределённый граничный случай, только если от него зависит выполнение требования.
5. Для принятого проектом ГОСТ Р 59194-2020 учитывайте область применения. Пункты 5.2 и 5.3 связывают требования с проверкой, критериями, подтверждающими документами и согласованием. Пункт 6.1.2 предусматривает организационные правила для текста требований. Пункт 6.2.2 требует устойчивого уникального идентификатора. При редактуре сохраните его, связи и версию. Содержание исходных требований и прохождение проверки подтверждаются разными источниками.

**Пример.** «Когда оператор повторно передаёт запрос с тем же `request_id`, сервис должен вернуть исходный `operation_id`». Для проверки сравните два ответа. Так можно проверить обещание вернуть тот же идентификатор. Вывод о повторной записи данных потребовал бы отдельного основания.

Паттерны EARS помогают выбрать конструкцию по событию, состоянию, функции или нежелательной ситуации. Если проект предписал EARS или ISO/IEC/IEEE 29148, соблюдайте принятый профиль. В обычной постановке выберите естественную формулировку по смыслу. [EARS](https://alistairmavin.com/ears/) · [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)

## API и сетевой протокол

В описании конкретного API точно передайте заданные элементы контракта. Например, при изменении значения поля сохраните его тип и регистр. Если контракт различает отсутствие поля, `null`, пустую строку и значение по умолчанию, сохраните эти различия. Отдельно проверьте версию контракта, действия сторон, повтор, тайм-аут и порядок сообщений, если они определены в источнике.

Если документ явно принимает BCP 14, сохраните оригинальные нормативные слова и регистр. По RFC 2119 и RFC 8174 `MUST`, `REQUIRED` и `SHALL` задают обязательное условие, `MUST NOT` и `SHALL NOT` задают запрет. `SHOULD` и `RECOMMENDED` допускают обоснованное отступление после рассмотрения последствий. `SHOULD NOT` и `NOT RECOMMENDED` допускают обоснованное исключение из отрицательной рекомендации. `MAY` и `OPTIONAL` разрешают выбор. При таком соглашении специальное значение имеют формы в верхнем регистре. Строчные слова трактуйте по контексту. В русском пояснении передайте ту же силу. Не добавляйте BCP 14 в договор, который его не принимал. [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) · [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)

**Пример.** Если контракт разрешает (`MAY`) вернуть `Retry-After` вместе с `429`, запишите «Сервер вправе включить заголовок `Retry-After` в ответ `429`». Случай без заголовка по этому условию допустим.

## Руководство, скилл и описание решения

- **Действие пользователя.** Дайте команду читателю. Назовите исходное состояние, элемент интерфейса и признак завершения, если они нужны для выполнения шага. Поставьте существенное исключение у того шага, который оно меняет. Метки опасности и предусмотренные остановки сохраняйте вместе с командой.
- **Скилл.** Опишите задачу скилла и ожидаемый результат. Если важны допустимые входы, границы действия, путь файла или условие остановки, укажите их. Если скилл только проверяет, сохраните эту границу. Термин «проверено» требует наблюдаемого результата проверки.
- **Архитектурное решение.** Сохраните принятое решение и известные основания выбора или пределы применимости. Если второй вариант отвергли из-за стоимости, не превращайте это решение в утверждение о его технической невозможности.
- **Протокол испытания или совещания.** Передайте зафиксированные наблюдения или решения. Сохраните известные условия, основания и участников, от которых зависит смысл записи. Если есть исполнитель, срок или критерий приёмки, сохраните их. Слова о будущем действии не подтверждают его выполнение.
